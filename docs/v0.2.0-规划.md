# v0.2.0 规划：让每个应用都有「作用」和「该不该动」

> 状态：**规划中，尚未实现**
> 前置版本：v0.1.1
> 本文件由维护者决策敲定，作为实现依据。

---

## 一、现状与差距

### v0.1.1 已经解决的

| 能力 | 实现方式 |
|---|---|
| 应用真实名字 | **直接从手机里的 APK 读**（`pm path` → `dd` 读 ZIP 中央目录 → `AndroidManifest.xml` → `resources.arsc`），不联网、不需要 API Key，且是桌面上显示的那个名字 |
| 表格「应用名」列 | 名单中文名 → APK 读出的真实名字 → 留空 |
| 表格「建议」列 | 受保护·不要动 / 受保护·默认留 / 名单·建议处理 / 名单·按需处理 / 名单·保留 / 常见应用·建议留 / 名单外·自行判断 |
| 说明列不再重复 | 名单里的写作用；系统应用按包名前缀归类 |
| 安装来源可读 | `installerNames` 把包名映射成中文 |

**关键结论**：应用「叫什么」这个问题已经用最优解解决了。网络查询在这一点上比不过本地解析——它慢、要清洗标题、覆盖不全，而 APK 里就是标准答案。

### 还缺什么

1. **名单外应用仍然没有「作用」**。APK 能读出名字，读不出"它是干什么的"。用户看到「超级爱清理」还是不知道该不该动。
2. **名单外应用的建议统一是「自行判断」**，等于没建议。
3. **懒人模式的白名单永远写不全**——地方政务、社区服务、医院自建 App 包名没有规律，写漏一个就是误删。**已决定废弃**。
4. 每台手机、每次扫描都在重复获取同样的信息，没有沉淀。

## 二、总体方案：三级查询链

查询的对象是**「作用说明 + 处理建议」**，不是名字。

```text
扫描到一个包
   │
   ├─ 应用名 ──────────► 本地 APK 解析（已实现，比任何网络查询都准）
   │
   └─ 作用与建议
        │
        ├─ ① 本地优先（命中即止，不发网络请求）
        │     packages.json / protected.json 里的手写信息
        │     → data/app-catalog.json        （离线库，随程序分发）
        │     → app-lookup-cache.json        （历史查询结果）
        │
        ├─ ② 在线反查（应用宝为主，多个备选接口依次尝试）
        │
        └─ ③ API Key 兜底（DeepSeek）
             │
             └─► 命中任何一层都写入 app-lookup-cache.json
```

**三条硬约束**：

1. **本地优先**。命中本地就不发网络请求，扫描速度不受影响。
2. **任何一层失败都不影响扫描**。在线查询超时、被限流、接口改版，都只是"这一层没结果"，直接往下走。
3. **这三层只提供信息，不做决策**。唯一的例外见第六节。

## 三、第 1 层：离线名称库（UAD 中文化）

### 数据来源

`Universal-Debloater-Alliance/universal-android-debloater-next-generation` 的
`resources/assets/uad_lists.json`：**5381 条**，社区长期维护。

字段结构（实测）：

```json
{
  "list": "Oem",
  "description": "Another overlay for com.miui.miwallpaper...",
  "removal": "Advanced",
  "dependencies": [],
  "neededBy": [],
  "labels": [],
  "suggestions": "cameras"
}
```

`removal` 分布：`Recommended` 3003 / `Advanced` 1158 / `Expert` 923 / `Unsafe` 297。

**许可**：已确认与本项目兼容，可以合并。

### 产物

新增 `data/app-catalog.json`：

```json
{
  "schemaVersion": 1,
  "generatedAt": "2026-09-25",
  "source": "uad_lists.json@<commit-sha>",
  "entries": {
    "com.miui.systemAdSolution": {
      "name": "系统广告服务",
      "summary": "小米系统级广告投放服务，负责在系统应用与通知栏插入推广内容",
      "removal": "recommended",
      "category": "广告与跟踪"
    }
  }
}
```

### 为什么和 `packages.json` 分开

| 文件 | 职责 | 规模 | 出错代价 | 维护方式 |
|---|---|---|---|---|
| `packages.json` / `protected.json` | **决策**：删/留/怎么删 | 小 | 高（会误删） | 人工把关 |
| `app-catalog.json` | **描述**：这是什么 | 大（可到几万条） | 低（只是显示错） | 脚本批量生成 |

分开之后，名称库可以放心地批量生成、频繁更新、接受社区随便补——**写错了顶多显示成别的名字，不会导致误删**。

### 生成脚本

`tools/build-app-catalog.py`，离线跑一次，产物进仓库：

1. 拉 UAD 清单，记录 commit sha 便于追溯
2. 批量机翻 `description`（**已确认机翻够用**）
3. 合并人工维护的覆盖项（优先级最高）
4. 输出 `data/app-catalog.json`，按包名排序

人工只需要维护"机翻错了"和"UAD 缺了"的部分。

### removal 到界面文案的映射

| UAD | 条数 | 建议列显示 | 默认勾选 |
|---|---|---|---|
| `Recommended` | 3003 | 建议清理 | ✅ |
| `Advanced` | 1158 | 可以清理·先确认 | ⬜ |
| `Expert` | 923 | 不建议普通用户动 | ⬜ |
| `Unsafe` | 297 | 不要动 | ⬜ |

**必须标注来源**：这些结论来自 UAD 社区，不是本项目的判断。界面上要能看出来。

### 已知限制

- **主要覆盖系统预装包**（`Oem` 4251 条），第三方应用基本没有
- 同一包名在不同机型上的结论可能不同，UAD 是通用建议
- 机翻质量参差，`Recommended` 里的高频条目建议人工过一遍

## 四、第 2 层：在线包名反查

定位：给 UAD 覆盖不到的**第三方应用**补上"这是什么、是否正规上架"。

### 接口适配器

每个接口实现同一个接口，按顺序尝试，**任何一个命中就停止**：

| 接口 | URL 模板 | 判定方式 | 验证状态 |
|---|---|---|---|
| 腾讯应用宝 | `https://sj.qq.com/appdetail/<包名>` | `404` = 未上架；`200` 且标题含「相关推荐」= 兜底页，等于没找到；否则命中 | ✅ **已实测** |
| Google Play | `https://play.google.com/store/apps/details?id=<包名>` | `404` = 未上架 | ✅ **已实测连通**（国内网络可能不通） |
| 华为应用市场 | 待定 | 待验证 | ⬜ |
| 小米应用商店 | 待定 | 待验证 | ⬜ |
| APKPure / APKCombo | 待定 | 待验证 | ⬜ |

> 国内部分网络环境访问 Google 会失败，属于预期情况，直接走下一个接口即可。

应用宝页面是服务端渲染，`og:title` / `og:description` 直接在 HTML 里，**不需要跑 JS、不需要 key、不需要登录**。

### 标题清洗

应用宝标题格式不统一，需要清洗，但**清洗失败宁可显示原文，绝不显示错的名字**：

```text
微信下载安装-微信APP官网客户端下载-应用宝官网      → 微信
淘宝app-官方正版软件2026最新版本免费下载-应用宝官网 → 淘宝
哔哩哔哩官网app下载-bilibili官网客户端[B站APP]      → 哔哩哔哩
超级爱清理官方版-相关推荐-应用宝官网                → 兜底页，丢弃
```

规则：取第一个 `-` 之前 → 剥离后缀词表（`下载安装` / `官网` / `app` / `官方版` / `下载`…）。词表写进数据文件，便于调整。

### 用途与边界

- **能拿到**：应用名（备用，本地解析失败时兜底）、一句话简介、是否在正规商店上架
- **拿不到**：是否恶意——正规上架的应用也可能是广告重灾区

**「未上架」只是信号，不是判决。** 企业内部分发、地方政务、医院自建 App 都可能没上架应用宝。它只能影响排序和提示，**绝不能变成自动勾选的依据**。

## 五、第 3 层：API Key 兜底

定位调整：**只判断"该不该留"，不负责认名字**。名字由本地 APK 解析和离线库提供。

### 触发条件

前两层都没有结果时才调用。默认关闭，用户填了 Key 并主动开启才生效。

### 输入要加权限画像

从 `dumpsys package` 的 requested permissions 稳定获取，这些是"推广类应用"的真正指纹：

| 信号 | 意义 |
|---|---|
| `REQUEST_INSTALL_PACKAGES` | 能自己安装应用 → 静默安装的核心能力 |
| `SYSTEM_ALERT_WINDOW` | 能弹悬浮窗 → 悬浮广告的核心能力 |
| 无障碍服务 | 流氓应用惯用手法 |
| 通知权限 | 推送广告 |

附带安装来源、首次安装时间、有没有桌面图标。

**好处是结论可解释**：可以直接告诉用户"这个应用能自己安装其它应用、能弹悬浮窗"，比"AI 觉得它不好"有说服力。

### 输出约束（沿用现有原则）

- 结果默认**不勾选**，必须人工确认
- 受保护名单里的应用**连问都不问**
- 低置信度一律作废

## 六、勾选策略调整：去除懒人模式

### 删除什么

| 位置 | 内容 |
|---|---|
| `data/packages.json` | `lazyMode` 整段配置 |
| `RuleModels.cs` | `LazyModeConfig` 记录类型 |
| `RuleRepository.cs` | `LazyMode` / `IsLazyModeKeep` |
| `PlanBuilder.cs` | `ApplyLazyMode` |
| `MainViewModel.cs` | `ApplyLazyModeCommand` 与界面提示 |
| `MainWindow.xaml` | 「懒人模式」面板 |
| `SelfTest.cs` | `[4d]` 懒人模式检查项 |
| `README.md` / `docs/名单格式说明.md` | 懒人模式章节 |

### 换成什么

**自动勾选的依据从「白名单之外」改成「有明确证据」**：

| 来源 | 条件 | 默认 |
|---|---|---|
| `app-catalog.json` | `removal = Recommended` | ✅ **勾选** |
| `app-catalog.json` | `removal = Advanced` | ⬜ 不勾，标注「可以清理·先确认」 |
| `app-catalog.json` | `removal = Expert` / `Unsafe` | ⬜ 不勾，明确标注不要动 |
| `packages.json` 规则 | 沿用现有 tier / risk / confidence 逻辑 | 现有逻辑 |
| 第三方应用 | UAD 无条目 | ⬜ 不勾，靠第 2/3 层补信息后人工判断 |

### 这样改的取舍

**好处**

- 依据变硬了：UAD 是社区长期验证的结论，比"白名单外全删"可靠得多
- **不会再有"白名单写漏就误删"的问题**——这是废弃懒人模式的核心原因
- 用户扫完直接点执行，不需要先点一个"一键勾选"按钮

**代价**

- **覆盖面收窄**：UAD 主要覆盖系统预装包，第三方流氓应用它不管
- 老人手机上半数以上的"莫名多出来的应用"是第三方应用，这部分回到"人工判断"

### 遗留问题（**需要决策**）

第三方流氓应用（UAD 无条目）怎么自动处理？三个选项：

| 方案 | 做法 | 风险 |
|---|---|---|
| **A（推荐）** | 只提供信息（名字 + 简介 + 权限画像 + 是否上架），按可疑度排序，默认不勾 | 需要人工过一遍，但零误伤 |
| **B** | 第 3 层 AI 判断，`confidence ≥ 0.9` 才自动勾 | 依赖 Key；AI 结论无法人工复核 |
| **C** | 高风险特征组合自动勾（能装应用 + 能弹悬浮窗 + 未上架） | 特征组合需要真机数据校准 |

建议**先做 A，观察一轮真实数据**（哪些包没被 UAD 覆盖、它们长什么样），再决定要不要做 B 或 C。

## 七、缓存设计

### 位置

```text
%LOCALAPPDATA%\AndroidOptimize\app-lookup-cache.json
```

与 `snapshots/` `reports/` `logs/` 保持一致。用户删掉程序目录不影响缓存，反之亦然。

> 待确认：这里按"用户数据目录"理解。如果要放程序目录（便于手动编辑 / 随程序带走），改一行配置即可。

### 结构

```json
{
  "schemaVersion": 1,
  "entries": {
    "com.taobao.taobao": {
      "status": "found",
      "name": "淘宝",
      "summary": "淘宝是一个好逛、丰富、有趣的消费生活社区…",
      "advice": "keep",
      "source": "yingyongbao",
      "fetchedAt": "2026-09-25T13:00:00+08:00"
    },
    "com.lucky.wifi": {
      "status": "not-found",
      "source": "yingyongbao",
      "fetchedAt": "2026-09-25T13:00:01+08:00",
      "expiresAt": "2026-10-25T13:00:01+08:00"
    }
  }
}
```

### 有效期策略

| 结果 | 有效期 | 理由 |
|---|---|---|
| 命中（有名字/简介） | **永久** | 应用身份不会变 |
| 未找到 | **30 天** | 避免把一次网络抖动永久记成"不存在"；也给新上架的应用留余地 |
| 查询失败（超时/限流） | **1 天** | 短期重试 |

### 其它

- 查询**串行 + 间隔 200~400ms**，避免被接口限流
- 单次扫描最多查 N 个（默认 60，可配置），超出的下次继续
- 界面提供「清空查询缓存」按钮
- 缓存文件损坏时静默重建，不影响扫描

## 十、明确不做的事

- **不再做第二份白名单。** 懒人模式的教训是：白名单永远写不全，写漏就是误删。
- **不用 LLM 认名字。** 本地 APK 解析是标准答案，离线库是补充，LLM 只做兜底判断。
- **不因为"查不到"就自动勾选。** 未上架只是信号，不是判决。
- **不动保护名单的优先级。** 反诈、支付、输入法、电话短信在任何逻辑下都是一票否决。
