# 名单格式说明

应用名单是这套工具的核心资产。程序与名单完全分离：**改名单不需要重新编译程序**，
只要替换 `data/packages.json` 或 `data/protected.json` 即可。

---

## 一、加载顺序

程序按下面的顺序找一个配置文件，找到就用，找不到就往下退：

1. `%LOCALAPPDATA%\AndroidOptimize\data\<文件名>`　← 用户数据目录（以后在线更新写这里）
2. `<程序目录>\data\<文件名>`　　　　　　　　　　← 发布包里带的
3. 程序内置的副本　　　　　　　　　　　　　　　　← 保底，保证离线也能跑

所以测试新名单时，把它丢到 `%LOCALAPPDATA%\AndroidOptimize\data\` 就能覆盖发布包里的版本。

## 二、packages.json

顶层结构：

```json
{
  "schemaVersion": 1,
  "listVersion": "2026.09.19.1",
  "updatedAt": "2026-09-19",
  "channel": "stable",
  "packages": [ ... ],
  "settings": [ ... ]
}
```

除了 `packages` 和 `settings`，还有第三个数组 `policies`（全局策略），见下文第四节。

还有一个顶层的 `installerNames` 映射，把安装来源包名换成中文。

以及 `permissionRisks`（值得警惕的权限），用来给每个应用打「权限画像」，见下文第六节。

### 应用规则字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✅ | 包名，例如 `com.xiaomi.market` |
| `name` | | 中文名称，界面和报告里显示这个 |
| `brands` | | 适用品牌，`["*"]` 表示全品牌。可用值：`xiaomi`/`redmi`/`poco`、`vivo`/`iqoo`、`oppo`/`oneplus`/`realme`、`huawei`、`honor`、`samsung` |
| `category` | | 分类，例如 `广告与跟踪`、`应用分发`、`快应用` |
| `tier` | ✅ | `normal` / `geek` / `danger`，决定它出现在哪个档位 |
| `risk` | ✅ | `low` / `medium` / `high`。`high` 永远不会被默认勾选 |
| `action` | ✅ | `disable` 停用 / `uninstall` 卸载 / `restrict` 后台限制 / `keep` 确认保留 |
| `confidence` | ✅ | 0~1，人工确认程度。低于当前档位门槛的条目不会被列出 |
| `reason` | | 为什么建议处理，一句话讲清楚 |
| `impact` | | 处理后会失去什么 |
| `appOps` | | 仅 `restrict` 使用，形如 `[{"op":"WAKE_LOCK","mode":"ignore"}]` |
| `standbyBucket` | | 仅 `restrict` 使用，通常是 `restricted`，失败会自动退回 `rare` |
| `ignoreSafetyMode` | | 为 `true` 时该项不受「安全模式」影响，始终按 `action` 执行。目前只用于应用商店 |

### 档位的置信度门槛

| 档位 | 最低 confidence | 效果 |
|---|---|---|
| 一般优化 | 0.75 | 只出现被反复验证过的条目 |
| 极客模式 | 0.50 | 含中等把握的条目 |
| 深度模式 | 0.00 | 全部列出，但低置信度项默认不勾选 |

这就是处理"这个包能不能删我不确定"的标准做法：**不确定就压低 confidence**，
而不是凭猜写进一般档位。程序会把它降级到深度模式，并且默认不勾选。

### 设置项字段

```json
{
  "id": "global.animation_scale",
  "name": "系统动画速度",
  "brands": ["*"],
  "category": "流畅度",
  "tier": "normal",
  "risk": "low",
  "action": "settings",
  "confidence": 0.95,
  "namespace": "global",
  "keys": ["window_animation_scale", "transition_animation_scale", "animator_duration_scale"],
  "choices": [
    { "label": "0.75x（推荐）", "value": "0.75" },
    { "label": "1x（系统默认）", "value": "1" }
  ],
  "defaultChoice": "0.75",
  "reason": "...",
  "impact": "..."
}
```

固定值用 `value`；需要用户挑选时用 `choices` + `defaultChoice`。

## 三、protected.json

```json
{
  "schemaVersion": 1,
  "listVersion": "2026.09.19.1",
  "patterns": [
    {
      "match": "com.android.providers.*",
      "level": "absolute",
      "category": "数据提供者",
      "reason": "联系人、短信、媒体等数据提供者，停用会导致数据丢失"
    }
  ]
}
```

`match` 支持 `*` 通配符（`*bank*`、`com.android.*`）。
匹配优先级：**精确匹配 > 更长的通配符**。

`level` 有两种：

| level | 含义 |
|---|---|
| `absolute` | 任何档位、任何来源（含 AI 建议）都不得操作 |
| `guarded` | 默认不勾选、AI 不得建议；用户打开「允许操作受保护应用」后可手动选择 |

判断某个包该进保护名单的经验法则：**删掉之后用户会"不会用手机"或"蒙受损失"的，一律 absolute。**
输入法、电话短信联系人、桌面、系统界面、安装器、无障碍、反诈、支付、银行、政务、医保，都属于这一类。

## 四、policies：全局策略

名单规则是「一个包一条」，而策略是「按条件作用到一批应用」。目前只有一条：传感器权限。

```json
{
  "id": "sensor_lock",
  "name": "关闭传感器权限（防摇一摇广告）",
  "category": "传感器权限",
  "tier": "normal",
  "risk": "low",
  "action": "restrict",
  "confidence": 0.8,
  "defaultEnabled": true,
  "scope": "thirdParty",
  "exclude": ["com.tencent.mm", "*map*", "*health*"],
  "appOps": [
    { "op": "BODY_SENSORS", "mode": "ignore" },
    { "op": "HIGH_SAMPLING_RATE_SENSORS", "mode": "ignore" },
    { "op": "ACTIVITY_RECOGNITION", "mode": "ignore" }
  ],
  "standbyBucket": null,
  "reason": "...",
  "impact": "..."
}
```

| 字段 | 说明 |
|---|---|
| `scope` | `thirdParty` 只作用于第三方应用；`all` 连系统应用一起 |
| `exclude` | 排除名单，支持 `*` 通配符。微信、地图、运动健康类都在这里 |
| `appOps` | 要下发的权限限制。**留空则只做 `standbyBucket`** |
| `standbyBucket` | 留空表示**不动后台策略**，只下发 `appOps` |

几点设计约束，改动时请遵守：

1. **保护名单永远优先于策略。** 即使 `exclude` 里写漏了微信，策略也不会碰到它。
2. **同一个应用只出一行。** 如果这个应用在 `packages` 里已经有 `restrict` 规则，
   策略的 `appOps` 会**合并进那一行**，而不是再出一条重复的。
3. **会被停用或卸载的应用不需要策略。** 都已经停掉了，再关传感器没有意义。
4. `scope` 建议保持 `thirdParty`。系统应用里有相机、指南针这类真的需要传感器的，
   放开会给用户带来莫名其妙的故障。

### 关于传感器限制的真实效果

标准 Android **没有**给加速度传感器设置权限门控，所以 ADB 能下发的只有上面这几项
（心率传感器、高采样率传感器、运动识别）。能挡到什么程度取决于系统版本与厂商实现。

程序对每一项都会**回读校验**，并在「执行结果」页如实显示通过还是失败，不会假装成功。
如果将来发现更有效的 op，直接加进 `appOps` 即可，不需要改代码。

## 五、installerNames：安装来源中文名

手机上记录的安装来源是包名（`com.xiaomi.market`），直接显示对用户没意义。
`installerNames` 把它换成中文：

```json
"installerNames": {
  "com.xiaomi.market": "小米应用商店",
  "com.android.packageinstaller": "本机安装",
  "com.tencent.android.qqdownloader": "应用宝"
}
```

没有对应项时原样显示包名。**它只影响显示**，不参与任何判断。

## 六、permissionRisks：值得警惕的权限

用来给每个应用打一份**权限画像**：扫描时顺带读一遍应用申请的权限，命中这里的条目就在
「手机体检」和「优化计划」的**权限**列上显示出来，也能按它筛选。

```json
"permissionRisks": [
  {
    "match": "SYSTEM_ALERT_WINDOW",
    "name": "悬浮窗",
    "risk": "high",
    "why": "可以在其它应用上层弹窗，悬浮广告和诱导点击的常用手段"
  }
]
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `match` | ✅ | 权限名里的关键字，用**包含**匹配（大小写不敏感）。写 `SYSTEM_ALERT_WINDOW` 能同时命中 `android.permission.SYSTEM_ALERT_WINDOW` 和厂商自定义的同类权限 |
| `name` | ✅ | 界面上显示的短名，例如「悬浮窗」。这一列宽度有限，尽量 4 个字以内 |
| `risk` | ✅ | `low` / `medium` / `high`。**high 决定「含高危权限」筛选的边界** |
| `why` | | 为什么值得警惕，鼠标悬停时显示 |

### 这一层刻意不参与决策

权限画像**不会**改变任何勾选状态，也不会进 `PlanBuilder` 的默认选择逻辑。原因是反例太多：
输入法要悬浮窗是为了悬浮键盘，录屏、投屏、车载应用也都要悬浮窗；相机类应用要读联系人可能是
为了分享。拿权限直接决定删不删，等于把「瞎猜」换了个地方。

它的职责只有一个：**帮用户在一堆不认识的包里找到最可疑的那几个**——
一个名册里查不到的应用，如果同时要了「悬浮窗」和「安装应用」，基本可以断定是推广类。

### 显示与筛选规则

- 列里只显示**中风险以上**的命中项，高风险在前，最多 3 个（超出显示「等 N 项」）。
  低风险（例如「发送通知」）不进这一列，否则整列都是噪音；悬停时会全部列出。
- 颜色：含高危=红，只有中风险=橙，读到了但没命中=灰，**没读到=「—」**。
  「没读到」刻意画成灰色而不是绿色：不知道不等于没问题。
- 筛选：`全部` / `含高危权限` / `无高危权限` / `未读取`，后面跟着 `permissionRisks` 里的每个 `name`。
  「无高危权限」只匹配**读到了**权限列表的应用，「未读取」单独一项。
- 排序用 `SortRank`：0=含高危、1=只有中风险、2=读到了但干净、3=未读取。
  **数值越小越可疑**，所以点一次「权限」列表头就是高危应用排在最前面。

### permissionCombos：值得警惕的权限组合

单条权限命中太散，单独拿来筛没什么用。真机实测（300 个包）：「悬浮窗」命中 84 个、
「读取所有应用」83 个、「安装应用」59 个，**任一高危权限命中 137 个**——这个筛选出来还是一长串。
但「悬浮窗 + 安装应用」只有 42 个，这才是能直接下手的名单：

```json
"permissionCombos": [
  {
    "name": "悬浮窗+安装应用",
    "allOf": ["SYSTEM_ALERT_WINDOW", "REQUEST_INSTALL_PACKAGES"],
    "risk": "high",
    "why": "既能悬浮弹窗、又能自己拉起安装其它应用，是推广与流氓类应用的典型组合"
  }
]
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | ✅ | 筛选下拉里显示的名字。**必须同时出现在下拉里**，所以要短、要一眼看懂 |
| `allOf` | ✅ | 必须**同时**命中的权限关键字，取值同 `permissionRisks.match` |
| `risk` | | `low` / `medium` / `high`，只用于说明 |
| `why` | | 为什么这个组合可疑，悬停时显示 |

组合名会出现在筛选下拉里（排在具体权限前面），选中就只看命中这个组合的应用。
组合命中也会写进权限列的悬停说明，所以看到「危险组合：悬浮窗+安装应用」就知道该重点看哪个。

要加新组合直接在名单里加一条即可，程序不用改；组合名不要和 `permissionRisks.name` 重名
（自检里有这一条检查）。

## 七、app-catalog.json：离线名册（只描述，不决策）

**这份文件不是名单，不要把它和 `packages.json` 混为一谈。** 分工是刻意的：

| 文件 | 职责 | 规模 | 出错代价 | 维护方式 |
|---|---|---|---|---|
| `packages.json` / `protected.json` | **决策**：删 / 留 / 怎么删 | 小 | 高（会误删） | 人工把关 |
| `app-catalog.json` | **描述**：这是什么 + 社区认为能不能动 | 大 | 低（只是显示错） | 脚本批量生成 |

分开之后，名册可以放心地批量生成、频繁更新、接受社区随便补。

### 来源与生成

数据来自 [Universal Android Debloater](https://github.com/Universal-Debloater-Alliance/universal-android-debloater-next-generation)
的 `uad_lists.json`（社区长期维护，5381 条），由脚本生成：

```powershell
python tools\build-app-catalog.py            # 用缓存，只翻译新增条目
python tools\build-app-catalog.py --refresh  # 重新下载 UAD 清单
```

结构：

```json
{
  "schemaVersion": 1,
  "generatedAt": "2026-09-25",
  "source": "Universal-Debloat-Alliance / ... uad_lists.json",
  "count": 5381,
  "translated": 5200,
  "entries": {
    "com.miui.misightservice": {
      "removal": "recommended",
      "list": "oem",
      "summary": "遥测与诊断收集应用，把分析数据发回小米服务器，对用户几乎没用。"
    }
  }
}
```

### removal → 界面表现

| removal | 建议列 | 默认勾选 | 进计划 |
|---|---|---|---|
| `recommended` | UAD·建议清理 | ✅ | 一般档及以上 |
| `advanced` | UAD·可清理 | ⬜ | 一般档及以上 |
| `expert` | UAD·不建议动 | ⬜ | 仅极客档及以上 |
| `unsafe` | UAD·不要动 | ⬜ | 从不 |

判定逻辑集中在 `RemovalAdvice`（`Models/CatalogModels.cs`），改这里就能调整策略。

### 人工校正

机翻难免出错，把要修正的写进 `tools/app-catalog-zh.json` 即可，优先级最高：

```json
{
  "com.miui.misightservice": "小米的遥测与诊断收集服务，会把使用数据发回服务器，建议清理。"
}
```

`packages.json` 与 `protected.json` 里已有的中文说明也会自动并入，不必重复写。

### 已知限制

- **主要覆盖系统预装包**（`Oem` 占 4251 条），第三方应用基本没有
- 结论是 UAD 社区的**通用建议**，同一包名在不同机型上可能不一样
- `summary` 是机器翻译，界面上会标注「UAD 社区资料」，出问题改 `app-catalog-zh.json`

## 八、维护名单的建议流程

1. **AI 建议 → 人工复核 → 进名单**。
   桌面版识别出的未知应用只作为建议，不要直接相信。确认过用途之后，
   再按上面的格式写一条记录进 `packages.json`，这才是名单长大的方式。

2. **不确定就压低 confidence**，让它落到深度模式，而不是混进一般档位。

3. **改完跑一次自检**：

   ```powershell
   AndroidOptimize.exe --selftest out.txt
   ```

   自检会校验名单能否解析、保护规则是否命中、各个档位的计划是否符合预期。

4. **发布前一定要升 `listVersion`**（推荐 `年.月.日.序号`），
   这样从用户日志里一眼就能看出用的是哪一版名单。

5. 涉及"是否该删"有争议的包，宁可先写成 `keep` 并写清 reason，
   也不要凭印象写进 `disable`。名单里的每一条都会直接作用在别人的手机上。
