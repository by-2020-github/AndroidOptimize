## 核心逻辑分层

`AndroidOptimize.Core` 按职责分成几层，依赖方向是单向的：

```text
Adb/          AdbClient（全命令带超时）、AdbLocator（找 adb）、AdbBootstrap（单文件发布时释放内嵌 adb）
  ↓
Apk/          ApkLabelSource  从真机读应用显示名（只读 APK 局部字节，不 pull 整包）
              ZipCentralDirectory / BinaryXml / ResourceTable —— ZIP + AXML + ARSC 解析
  ↓
Services/     DeviceScanner  扫描：6 次批量查询拿全量状态，可选深度读安装来源 + 权限列表
              AppLabelCache  应用名缓存（key 带版本号）
              AppCatalog     离线名册：包名 → 「这是什么 + 社区认为能不能动」
              Advice         建议的唯一出处（见下）：列表展示、筛选、默认勾选都走它
              PermissionAdvice 权限画像（见下）：按 permissionRisks 匹配，只展示与筛选
              DataFileLoader 数据文件的统一加载（用户目录 → 程序目录 → 内置）
              RuleRepository 名单加载：用户目录 → 程序目录 → 内置，三级回落
              PlanBuilder    计划引擎（纯函数）：名单 + 设备状态 + 档位 → 可预览的计划
              SnapshotStore  快照读写
              OptimizationExecutor  先快照 → 逐项执行 → 回读校验
              RollbackService       按快照还原
              ReportWriter / RunLogger / AppSettings / AppPaths / SecretProtector
  ↓
Ai/           DeepSeekClassifier（只识别不决策）、ClassificationCache
Testing/      SimulatedAdbClient、DemoDevice（无真机也能跑完整流程）
DeviceProbe.cs 真机只读体检：`--devicescan`，出报告不发散
SelfTest.cs   210 项自检
```

几个刻意的设计约束，改动时请保持：

1. **PlanBuilder 是纯函数**——不接触设备，只根据输入算出「将要做什么」，因此可以在执行前完整展示、也能单元测试。
2. **保护名单优先于一切**，优先级高于档位、高于 AI 建议。
3. **执行前必须落快照**，没有快照不执行。
4. **执行后必须回读校验**，不能只看命令有没有报错。
5. **AI 只做命名与归类**，不产生自动执行的动作。
6. **权限画像只用于展示与筛选**，不参与任何自动勾选（见「权限画像」一节）。
7. **不可逆的操作必须先把退路留好**（见「卸载前必须备份安装包」一节）。

### 应用名是怎么读出来的

名单里没有的应用只有包名，用户看不懂，所以程序会自己去 APK 里读应用名。
难点在于**不能把整个 APK 拉回来**（动辄几十 MB），做法是只读需要的几段字节：

```text
1. pm path <包名>                  → 拿到 base.apk 的路径
2. wc -c < base.apk               → 文件大小
3. dd 读末尾 128KB                 → 解析 ZIP 中央目录，得到各条目的偏移与长度
4. dd 读 AndroidManifest.xml       → 找出 <application android:label="...">
5. 如果 label 是资源引用（@string/app_name）：
   dd 读 resources.arsc            → 解析资源表，把资源 ID 换成字符串
```

每个应用通常只传几百 KB，结果是**手机上显示的真实名字**（如「极速清理大师」）。
三个解析器都在 `Apk/` 下，都做了严格的边界检查：任何一步不认识就返回 null，
界面回退到包名，绝不影响扫描。

> 用 `adb exec-out` 读二进制（普通 `adb shell` 会做换行转换，把二进制弄坏），
> 见 `AdbClient.ExecOutBytesAsync`。

#### 这里踩过的三个坑（改这个模块前先看）

1. **ZIP 中央目录不一定在尾块里。** 早期只读末尾 128 KB，然后要求中央目录完整落在里面。
   真机实测：20 个第三方应用里有 **17 个**不满足（条目数过万，中央目录 100 KB ~ 3 MB），
   于是这些应用全都读不出名字。现在先读尾块、从 EOCD 拿到中央目录的位置与大小，
   不在尾块里就**再单独读一次中央目录**（`ZipCentralDirectory.Locate` + `Parse` 两步）。
2. **失败要记住，也要说出来。** 早期失败只 `return null`，既不打日志也不进缓存：
   表现是「应用名读不出来 → 不进缓存 → 下次扫描再读一遍 → 还是读不出来」，
   用户看到的是「每次扫描都全扫一遍」。现在读不出来会写进缓存（空字符串 + `ReaderVersion`），
   下次直接跳过；失败原因也会进日志（`ApkLabelSource.Fail`）。
   改了读取逻辑就把 `AppLabelCache.ReaderVersion` 加一，旧的失败记录会作废并重试。
3. **有些包本来就没有应用名。** RRO overlay（`com.android.*.overlay*`）、
   `com.android.internal.systemui.*` 这类系统内部组件，manifest 里就没有 `android:label`。
   它们不会被列进「未知应用」，读不出来是正常的，别去追。

真机实测（Redmi / Android 16，353 个需要读名字的应用）：第一次 71 秒读出 174 个，
第二次补齐到 234 个，之后**每次 8 秒**（353 个全部命中缓存，其中 119 个是「已知读不出」）。
剩下的 8 秒是逐个 `dumpsys` 拿安装来源与权限的那一步。

### 三份数据的分工（不要混）

| 文件 | 职责 | 规模 | 出错代价 | 维护 |
|---|---|---|---|---|
| `data/packages.json` | **决策**：删 / 留 / 怎么删 | 小 | 高（会误删） | 人工把关 |
| `data/protected.json` | **决策**：绝对不能动 | 小 | 高 | 人工把关 |
| `data/app-catalog.json` | **描述**：这是什么 + 社区认为能不能动 | 5381 条 | 低（显示不对） | 脚本批量生成 |

名册由 `tools/build-app-catalog.py` 从 UAD 的 `uad_lists.json` 生成，机器翻译 +
`tools/app-catalog-zh.json` 人工校正。**它只描述、不决策**，所以可以放心批量更新。

**翻译走本机的 Hy-MT2 服务**（见 `\\wsl.localhost\Ubuntu-22.04\home\by\hy-mt2\AGENT_API.md`）：
llama.cpp 起的一个 7B 翻译模型，OpenAI 兼容接口，一次一批 + `json_schema` 结构化输出，
30 条约 30 秒、5381 条约 42 分钟，不会像免费接口那样被限流。

```powershell
# 服务不自启，先拉起来
wsl -u by -d Ubuntu-22.04 -- bash -lc "cd ~/hy-mt2 && ./bin/hy up 7b"
python tools\build-app-catalog.py                  # 默认用它翻译
python tools\build-app-catalog.py --translator none # 只组装，不翻译
```

服务没起来时脚本会探活失败并**跳过翻译**（保留英文原文），不会让构建失败。
译文缓存在 `tools/catalog-i18n-cache.json`（随仓库提交），**再跑一次只会补没翻过的**。

> 当前覆盖率 5317 / 5381 = 98.8%。剩下 64 条是 UAD 本身就没写描述的条目。

### ⚠️ UAD 的 removal 语义（踩过的坑）

`Recommended` 的含义是「**删了不会搞坏系统，你还能从商店装回来**」，
**不是**「这个应用是垃圾」。

实测：OEM 预装的 WPS、高德地图、百度、小红书在 UAD 里全是 `Recommended`。
早期版本直接拿它当自动勾选依据，会导致把这些用户真在用的应用一起清掉。

**最终规则**：`Recommended` **且「桌面上没有图标」** 才默认勾选。

理由：没有图标说明用户根本打不开它，只能是后台的推广/遥测组件；
有图标就说明它面向用户，**绝不能替用户决定删掉**。

「有没有图标」从 `dumpsys package` 里是否出现 `android.intent.category.LAUNCHER` 判断，
见 `DeviceScanner.ParsePackageDetail`。拿不到这个信息时不勾选（保守）。

### 「建议」是唯一的选择依据

程序里**没有白名单 / 黑名单**这种东西。每一条的处理建议都必须有出处：

```text
保护名单命中        → 受保护·不要动 / 受保护·默认留   （不参与选择）
packages.json 规则  → 名单·建议处理 / 按需处理 / 保留
app-catalog.json    → UAD·建议清理 / 可清理 / 不建议动 / 不要动
都没有              → 名单外·自行判断
```

`Models/Advice.cs` 是这套口径的唯一出处，`AdviceGroup` 同时驱动界面筛选。
**手机体检表和优化计划表用的是同一个方法**，所以同一行在哪儿看都是同一句话，
不会出现「体检说可以清、计划里却没勾」的矛盾。

计划里的默认勾选只认一条：`名册说 recommended 且没有桌面图标`。
没有任何「因为它不在某个清单里，所以自动处理」的逻辑——
这是之前废弃懒人模式留下的教训。

**动作可以手改**：`PlanItem.ActionOverride`（`EffectiveAction = ActionOverride ?? Action`）。
用户在「优化计划」页把某一行改成停用/卸载时，写的是这个覆盖值——
它是**显式选择**，所以不受安全模式降级（和执行器的 `IgnoreSafetyMode` 是同一个道理）。
改这个字段时记住：执行器、快照、`SelectionSummary` 都必须用 `EffectiveAction`，
用回 `Action` 就会出现「界面显示卸载、实际执行停用」这种最危险的偏差。

计划页上「停用 / 卸载」两个按钮是**立即执行**，不是改计划：
`ExecuteSelectedActionAsync` 把勾选的行（按包名去重，因为同一個应用可能同时有
「后台限制」行和「应用」行）临时挂上 `ActionOverride`，现拼一个只含这些项的
`OptimizationPlan` 交给同一个执行器（快照 → 逐项执行 → 回读校验 → 报告），
执行完在 `finally` 里把 `ActionOverride` 摘掉——「计划里的动作」和「这一次的执行」是两件事，
混在一起会出现「执行过的行还挂着覆盖值」的脏状态。执行完自动再扫一次（走缓存，1 秒内），
让列表反映手机的真实状态。

> 顺带记一下「从没打开过」这个信息（`dumpsys package` 的 `notLaunched`）：
> 它只作为说明列里的参考，**不参与任何自动勾选**——被其它应用唤醒也算启动过，
> 而流氓应用恰恰最会互相唤醒。

### 权限画像（帮用户找可疑应用，不替用户做决定）

**权限与安装来源会缓存**（`AppDetailCache`，key = `包名@版本号#读取版本`）：
申请了哪些权限写在 APK 里，应用不更新就不会变，所以缓存是安全的，
也是把重复扫描从 10 秒压到 1 秒的关键（真机实测：353 个应用 10.5 秒 → **0.6 秒**）。
需要「此刻的真实状态」时走 `forceRefreshDetails: true`（界面上的「强制重新读取权限」勾选、
命令行的 `--devicescan out.txt --force`）。
要注意的是「从未启动过」这类**运行状态**也跟着缓存，可能是上次扫描的结果——
说明列里写的是「系统记录」，界面上也提示了用强制读取拿最新。

扫描时顺手读一遍每个应用申请的权限（同一份 `dumpsys package` 输出里的
`requested permissions:` 段），和 `packages.json` 的 `permissionRisks` 匹配，得到一份「权限画像」：
命中哪些值得警惕的权限、最高风险是什么。这份画像有两个去处：

- **手机体检 / 优化计划**的「权限」列：显示高风险在前的最多 2 个短名（列宽有限，其余看悬停）；
- **权限筛选**：`全部 / 含高危权限 / 无高危权限 / 未读取` + 名单里的每条权限名。

`Models/PermissionProfile.cs` 是唯一出处（`AppPermissionProfile` + `PermissionAdvice`）。

单条权限命中太散（真机实测：300 个包里「悬浮窗」84 个、「读取所有应用」83 个，
任一高危 137 个，筛出来还是一长串），所以名单里还有 `permissionCombos`
（必须**同时**命中的权限），组合名也会出现在筛选下拉里 —— 「悬浮窗+安装应用」实测只有 42 个，
才是能直接下手的名单。

三个刻意的设计决定，改的时候别推翻：

1. **不参与决策**。输入法要悬浮窗是为了悬浮键盘，录屏、投屏也都要，拿权限决定删不删等于换一种瞎猜。
   它对 `PlanBuilder` 的默认勾选没有任何影响。
2. **「没读到」≠「没问题」**。`Permissions == null`（关掉深度扫描、或设备没输出这一段）时
   `Known=false`，列里显示「—」，颜色是灰色，筛选里单独一项「未读取」，
   而且**不会被「无高危权限」筛中**。绿色只能代表「读到了、没有命中」。
3. **解析要宽容**。各家 ROM 排版不同：老版本是纯权限名，Android 13+ 是 `权限名: granted=true`。
   `DeviceScanner.ParseRequestedPermissions` 按「段头 + 更深缩进 + 长得像权限名」取，
   遇到 `install permissions:`（缩进回到段头同级、或以 `:` 结尾）才结束；
   **找不到段头返回 `null` 而不是空列表**。
   注意段内会夹进 `MediaStore.Images.Media.EXTERNAL_CONTENT_URI` 这类杂物，
   甚至厂商拼错的 `ACCESS_WIFI_ STATE`（带空格）——遇到不像权限的行**只跳过、不结束**，
   早期版本一碰到带空格的条目就收尾，结果只读到前几条权限。

权限只在深度扫描的目标集合上读（第三方应用 + 名册里可处理的系统应用），
不为几百个纯内部系统组件白跑一遍 `dumpsys`。

> ⚠️ **别再用一个数字卡掉整层功能**：早期是「需要逐个读的应用超过 150 个就整段跳过深度扫描」，
> 结果是 140 个第三方应用的手机（很常见）**既没有安装来源、也没有权限**，
> 用户看到的是一整列「—」，而日志里连一次 `dumpsys` 都没有。
> 现在 `DetailScanLimit` 提到 400（真机实测单包约 100 毫秒，4 路并发下 400 个约 10 秒），
> 读应用名则单独设了 `LabelReadPerScan` 批次：超上限时**分批读并进缓存**，
> 再扫一次继续补，而不是干脆不读。

### 卸载前必须备份安装包（踩过的坑，别再踩）

**`pm uninstall --user 0` 对商店安装的应用会把安装包一起删掉。** 真机上验证过：
卸载后 `dumpsys package` 里 codePath 还在（残留记录），但那个目录里**一个 apk 都不剩**，
`cmd package install-existing` 自然也就装不回来（它只对系统分区上还有副本的应用有效——
系统预装应用、以及被更新过的系统应用，后者带 `UPDATED_SYSTEM_APP` 标记）。

这个坑的代价：用户手机上有 9 个商店应用（百度输入法、讯飞输入法、百度地图、薄荷健康、
中国广电、小游戏中心、CarLife…）卸载后永久丢失，只能重新下载。**所以现在没有备份就不卸**：

1. `OptimizationExecutor` 在**落快照阶段**（`CaptureSnapshotAsync`）就把安装包拉到
   `devices\<序列号>\apk-backup\<包名>\`（base.apk + 所有 split，用 `adb pull`）。
2. `SnapshotEntry` 记下 `IsSystem` 与 `ApkBackupDirectory`/`ApkBackupBytes`。
3. **备份失败 → 这一项直接跳过执行**（`backupSkipped` 列表），结果里如实写「为避免卸载后无法恢复，已跳过」。
   宁可不动，也不做不可逆的事。
4. 回滚时 `RollbackService` 先看有没有备份：有就用 `install-multiple -r` 装回，
   没有才退回 `install-existing`，两者都不行就明确告诉用户「需要重新下载」。
5. `RestorabilityChecker` 在回滚页做**只读**判断（备份？系统标记？codePath 目录里还有 apk？），
   让用户在点「一键还原」之前就知道哪些救不回来。

界面上对应的开关是 `AppSettings.BackupApksBeforeUninstall`（默认开，第 3 步可关），
关掉时卸载确认框会明确警告「这几个卸载之后装不回来」。

### 多台手机的数据归档（给一群人做优化时的底座）

目标是「拿这个工具给亲戚朋友挨个优化，顺便积累数据来改进名单」。所以数据必须**按序列号分开**，
而且要能汇总成一份能直接看的报告。落地在 `Services/DeviceArchive.cs`：

```text
%LOCALAPPDATA%\AndroidOptimize\
├─ label-cache.json / ai-cache.json      跨手机共用（key 是包名+版本，换手机照样命中）
└─ devices\<序列号>\
    ├─ device.json      机型/品牌/ROM/Android/首见时间/扫描次数/执行次数
    ├─ scans\           每次扫描的完整快照（应用、来源、权限、建议），留最近 10 次
    ├─ executions\      每次执行做了什么、回读校验过没过，留最近 20 次
    ├─ snapshots\       回滚快照（SnapshotStore 传序列号就落在这里）
    └─ reports\         体检报告、执行报告
```

几个刻意的决定：

1. **缓存跨手机共用，档案按手机分开。** 应用名与 AI 结论只跟「包名+版本」有关，
   跟哪台手机无关，共用才能越用越快；而「这台手机装了什么」必须分开，否则统计会被算重。
   合并统计时每台手机只取**最近一次**扫描。
2. **回滚列表只列当前这台手机的快照。** 主要不是整洁，是安全：把 A 手机的快照还原到 B 手机上
   只会把 B 搞乱。旧版本留在全局 `snapshots\` 里的快照按 `DeviceSerial` 过滤后仍然能用。
3. **演示模式不写档案。** 虚拟手机的序列号是 DEMO0000，混进统计里就是脏数据，
   所以 `MainViewModel` 里对归档做了 `!IsDemoMode` 的短路。
4. **统计报告必须能直接外发。** `BuildStatistics` 只输出机型、系统版本、包名、权限名，
   设备用「设备 1/2/3」编号，**不写序列号**（自检里有一条断言盯着这一点）。
   最有用的是第三节「名单外的第三方应用」和第五节「还没收录的权限」——
   前者是补 `packages.json` 的候选，后者是补 `permissionRisks` 的候选。
   第五节刻意滤掉了联网/相机/定位这类日常权限，否则排行榜全被它们占满，看不出问题。
5. **归档失败不影响主流程。** 写文件出问题只记一条 warning，扫描结果照常展示。

自检里所有归档方法都带 `devicesRoot` 重载，测试写到临时目录，
不会把 `SIMPERM` 这种测试设备混进用户真实的手机档案。

## 打包

```powershell
.\tools\publish.ps1                               # 单文件 exe（约 70MB，发 Release 用）
.\tools\publish.ps1 -Folder                       # 文件夹形式，便于手工改名单
.\tools\publish.ps1 -Folder -FrameworkDependent   # 依赖 .NET 8 桌面运行时（约 18MB）
.\tools\publish.ps1 -Version 0.1.0                # 文件名带上版本号
.\tools\publish.ps1 -OutputDirectory release -Version 0.1.0   # 输出到要提交的目录
```

打包脚本会**对产物本身跑一遍自检**，不通过就不产出。

### 单文件是怎么做到的

`adb.exe` 和两个 Windows USB 驱动库被作为 `EmbeddedResource` 编进 `AndroidOptimize.Core`，
首次运行时由 `AdbBootstrap` 释放到 `%LOCALAPPDATA%\AndroidOptimize\platform-tools\`。
名单也内置了一份兜底副本。所以单个 exe 在完全空白的目录里也能跑（已由自检验证）。

> 注意：`AdbBootstrap` 用 SHA256 比对内容，内容一致就不重复写盘——adb 正在运行时文件被占用也不会出错。

## 自检与诊断入口

```powershell
AndroidOptimize.exe --selftest out.txt       # 210 项逻辑自检
AndroidOptimize.exe --uicheck out.txt        # 界面与样式加载检查
AndroidOptimize.exe --demo                   # 演示模式：虚拟手机，不连接真机
AndroidOptimize.exe --demo 1                 # 演示模式并直接切到第 1 个页签
AndroidOptimize.exe --shots <目录>            # 生成文档截图
AndroidOptimize.exe --rendercheck out.png    # 检查当前环境能否做离屏渲染
AndroidOptimize.exe --plancheck out.txt      # 流程检查：筛选 → 批量勾选的范围对不对
AndroidOptimize.exe --devicescan out.txt     # **真机**只读扫描报告（不改手机，排障用）
AndroidOptimize.exe --stats out.md           # 汇总所有手机的档案，出匿名统计（不连手机）
AndroidOptimize.exe --uiclick out.txt        # 真的点一下计划页的按钮，验证界面不是「点了没反应」
```

`--plancheck` 在虚拟设备上跑一遍「扫描 → 筛选「建议清理」→ 全不选 → 全选」，
确认批量勾选**只作用于筛选结果**、被筛掉的行一个都没被动过。
它不需要真机，改动列表/筛选/勾选逻辑后值得跑一次。

`--devicescan` 连上真机跑一遍完整的只读扫描（`pm list` + `dumpsys` + 读 APK 局部字节），
报告里写清：有没有执行深度扫描、有多少应用读到了权限、哪些应用命中了高危权限与危险组合。
**不动手机上的任何东西。** 遇到「权限列怎么是空的」「应用名怎么没读出来」这类问题，
让用户跑一次并发这个文件过来，比来回猜快得多。

`--selftest` 覆盖的内容：

- 内置 adb 释放（含幂等性）、名单加载、保护规则命中
- 各档位的计划生成是否符合预期（含「应用商店在安全模式下仍卸载」「策略排除微信/地图」）
- **模拟设备上的端到端演练**：扫描 → 计划 → 执行 → 回读校验 → 回滚 → 再扫描
- 快照读写、报告生成、API Key 加密

## 界面截图是怎么生成的

```powershell
.\tools\capture-screenshots.ps1      # → assets/
python tools\make-diagrams.py        # → assets/
```

截图不走屏幕抓取，而是**程序自己的演示模式 + 离屏渲染**，内容与真实界面一致，
在远程桌面、CI 环境里也能生成。

踩过的两个坑，已修：

1. 直接渲染 `Window` 会得到空白图，必须渲染窗口的**内容根元素**；
2. 窗口从未真正显示过时，第一次 `Measure/Arrange` 只展开外层模板，
   表格行列要到下一轮才生成——所以渲染前要**预热一次布局**并让出一轮消息循环。

> 在桌面会话处于「断开」或锁屏状态时，WPF 渲染不出画面（连纯色方块都是空白）。
> 脚本会检测到并生成明确标注的占位图，避免文档出现坏链。

## 发布流程

打一个 `v` 开头的 tag，GitHub Actions 会自动编译、跑自检、挂到 Release：

```powershell
git tag v0.1.0
git push origin v0.1.0
```

工作流文件：`.github/workflows/release.yml`（发布）、`.github/workflows/build.yml`（每次 push 跑自检）。

### 关于把 exe 提交进 Git

`release/` 目录里放了打包好的 exe，方便直接从仓库下载。代价是**仓库历史永久增大**，
每版本约 70MB，且删掉文件也不会让 `.git` 变小。更推荐用 Releases（附件不占仓库体积）。
详见 [release/README.md](../release/README.md)。
